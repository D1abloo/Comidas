# Auditoría integral — BocadO

Fecha: 27 de julio de 2026  
Base auditada: `a1cb304` (`main`)  
Respaldo previo: bundle Git local fuera del repositorio

## 1. Resumen ejecutivo

El repositorio tenía una interfaz amplia y funcional en modo demostración, pero
mezclaba persistencia en memoria, PostgreSQL y documentación antigua de
Supabase/Vercel. Los riesgos más graves eran la simulación de pagos utilizable
como si fuese real, autorización de pedidos por coincidencia de email, secretos
con valores de reserva, transiciones de pedido no atómicas, facturas y catálogo
no persistentes y dependencias con vulnerabilidades conocidas.

Se ejecutaron las fases 0–6. Los hallazgos técnicos críticos y altos que podían
resolverse dentro del repositorio quedaron corregidos. TPV/Bizum reales, textos
legales definitivos, credenciales operativas, backups externos y publicación
siguen siendo tareas externas y permanecen explícitamente deshabilitadas o
documentadas.

## 2. Arquitectura actual

```text
Cliente web / PWA / WebViews Capacitor
                │ HTTPS + sesión HttpOnly
                ▼
Astro 7 SSR (Node standalone) + React islands
                │
        servicios de dominio
                │
      PostgreSQL 16 / store demo local
```

- `apps/web`: tienda, cliente, administración, reparto, API y generación PDF.
- `apps/mobile-app`: WebView Android unificada para admin y reparto.
- `apps/admin-app`, `apps/courier-app`: envoltorios heredados compatibles.
- `docker/postgres`: esquema inicial y migraciones aditivas.
- `scripts`: migración, smoke test y despliegue VPS/nginx.
- `tests`: validación de entrada, tokens, redirects y rutas seguras.

Puntos de entrada principales: `src/pages`, `src/middleware.ts`,
`src/server/db.ts`, `src/server/order-service.ts`, `src/server/pg.ts` y
`dist/server/entry.mjs` en producción.

- Cuenta: registro/login, histórico aislado por `user_id`, ticket y factura.
- Admin: platos, secciones, usuarios, ajustes, pedidos, facturas y avisos.

## 5. Hallazgos y resolución

### CRÍTICO — Pagos simulados podían confundirse con producción

- Impacto: pedidos marcados como pagados sin confirmación de proveedor.
- Evidencia original: `src/pages/api/payments/start.ts` y
  `bizum-confirm.ts`.
- Resolución: simulación limitada a desarrollo explícito; TPV/Bizum
  deshabilitados por defecto; producción devuelve indisponible.
- Pendiente externo: integrar Redsys/Stripe/Bizum y validar webhook.
- Dificultad externa: alta. Riesgo del cambio aplicado: bajo.

### CRÍTICO — Acceso horizontal a pedidos por email

- Impacto: una cuenta podía heredar pedidos creados con el mismo email.
- Evidencia original: `api/orders/index.ts`, `pedidos.astro`.
- Resolución: autorización e histórico exclusivamente por `customer.user_id`
  o token de acceso firmado y ligado al pedido.
- Dificultad: media. Riesgo aplicado: medio (pedidos invitados antiguos
  requieren su token).

### CRÍTICO — Secretos inseguros y compartidos

- Impacto: falsificación de sesiones o enlaces de pedido.
- Evidencia original: valores por defecto en seguridad y Compose.
- Resolución: secretos de sesión y pedido separados, mínimo de 32 caracteres,
  comprobación al arrancar y variables obligatorias en Docker.
- Dificultad: baja. Riesgo aplicado: despliegues mal configurados fallan pronto.

### ALTO — Estados y asignación de reparto no atómicos

- Impacto: dos repartidores podían aceptar el mismo pedido; saltos inválidos.
- Evidencia: servicios/rutas de reparto y estado.
- Resolución: `UPDATE ... WHERE` condicional, máquina de estados estricta,
  asignación exacta para ubicación/entrega y confirmación de pago previa.
- Dificultad: media. Riesgo aplicado: bajo.

### ALTO — Importes, IVA y payload del pedido insuficientemente validados

- Impacto: cantidades anómalas, payloads enormes y facturas incorrectas.
- Resolución: límite de 64 KiB, longitudes/cantidades acotadas, catálogo como
  fuente única de precios, IVA inclusivo por línea y envío, transacción SQL.
- Evidencia actual: `server/order-input.ts`, `api/orders/index.ts`.
- Dificultad: media. Riesgo aplicado: bajo.

### ALTO — Persistencia parcial y numeración de factura no segura

- Impacto: pérdida de catálogo/avisos/facturas y números duplicados.
- Resolución: persistencia PostgreSQL, contador transaccional por año/prefijo,
  factura única por pedido y outbox de notificaciones.
- Evidencia: `invoices-db.ts`, `catalog-db.ts`, `notifications-db.ts`.
- Dificultad: alta. Riesgo aplicado: medio, mitigado con migración aditiva.

### ALTO — Dependencias y runtime obsoletos

- Impacto: vulnerabilidades transitivas y soporte finalizado.
- Resolución: Astro 7, Node 22, Capacitor 8, Gradle 8.14.3; adaptador Vercel
  vulnerable/incompatible retirado; auditoría npm sin vulnerabilidades.
- Dificultad: alta. Riesgo aplicado: medio.

### ALTO — Docker/despliegue con credenciales de reserva y sin migraciones

- Impacto: base expuesta a claves predecibles o esquema desalineado.
- Resolución: secretos obligatorios, usuario no root, healthcheck,
  `no-new-privileges`, migrador con advisory lock y dependencia de arranque.
- Evidencia: `Dockerfile`, `docker-compose.yml`, `migrate-db.mjs`.
- Dificultad: media. Riesgo aplicado: bajo.

### MEDIO — Accesibilidad de overlays y controles

- Impacto: teclado/lector de pantalla atrapado o capaz de llegar al fondo.
- Resolución: foco inicial, trampa de foco, Escape, retorno de foco, diálogos y
  switches semánticos, targets de 44 px, live regions y skip link.
- Evidencia: `useDialogFocus.ts`, `CartDrawer.tsx`, `DishesBoard.tsx`.
- Dificultad: media. Riesgo aplicado: bajo.

### MEDIO — Checkout divergía de los ajustes del servidor

- Impacto: total mostrado y método elegido podían no coincidir con el pedido.
- Resolución: tarifa, umbral y métodos se renderizan desde ajustes; servidor
  continúa recalculando todo.
- Evidencia: `checkout.astro`, `CheckoutForm.tsx`.
- Dificultad: baja. Riesgo aplicado: bajo.

### MEDIO — Errores y estados de guardado ausentes

- Impacto: operaciones fallidas parecían correctas.
- Resolución: rollback optimista, `aria-busy`, mensajes `role=alert/status` en
  platos, checkout, Bizum y ajustes.
- Dificultad: baja. Riesgo aplicado: bajo.

### MEDIO — Rendimiento de portada y middleware

- Impacto: lectura completa de pedidos y catálogo/configuración en cada request.
- Resolución: agregado SQL de ventas y una hidratación por proceso.
- Dificultad: media. Riesgo aplicado: bajo.

### MEDIO — Seguridad Android

- Impacto: tráfico claro, backups y permisos de ubicación excesivos.
- Resolución: HTTPS obligatorio en producción, HTTP limitado al emulador,
  backups desactivados, permisos de background eliminados, minificación release.
- Dificultad: media. Riesgo aplicado: puede exigir foreground para ubicación.

### BAJO — Código y configuración muertos

- Evidencia: `Logo.astro`, `CartButton.tsx`, `server/courier-location.ts`,
  dos `vercel.json`.
- Resolución: eliminados tras confirmar ausencia de imports; documentación de
  Vercel sustituida por el estado soportado.
- Dificultad: baja. Riesgo aplicado: bajo.

## 6. UX y diseño

Se mantuvo la dirección visual editorial existente y se normalizaron tipografía
local, jerarquía, responsive del checkout, navegación móvil, estados de control
y metadatos. Las fuentes ya no dependen de Google Fonts. Se añadieron canonical,
Open Graph, Twitter cards, JSON-LD, `robots.txt` y sitemap.

## 7. Móvil

Las tres aplicaciones sincronizan el frontend remoto; no contienen un cliente
offline independiente. La unificada es la recomendada. No se pudo compilar APK
en esta máquina porque no hay JDK 21/Android SDK. La sincronización Capacitor sí
es comprobable sin publicar ni contactar servicios reales.

## 8. Limitaciones y riesgos residuales

1. **ALTO, externo:** TPV/Bizum reales no integrados. Permanecen desactivados.
2. **ALTO, externo:** textos fiscales/privacidad/cookies requieren validación
   legal y datos reales del negocio.
3. **MEDIO:** rate limiting es por proceso; para varias réplicas debe pasar a
   Redis/proxy compartido.
4. **MEDIO:** sesiones del adaptador Node usan filesystem; una topología
   multi-réplica necesita almacenamiento compartido.
5. **MEDIO:** las apps WebView no ofrecen modo offline completo.
6. **MEDIO, operativo:** faltan ensayo real de restauración, monitorización y
   alertas del VPS.
7. **BAJO:** `apps/admin-app` y `apps/courier-app` duplican la app unificada,
   pero se conservan para no romper distribución heredada.

## 9. Validación

```text
npm ci / npm install
npm audit

npm test
npm run build / npm run check
npx cap migrate --noprompt (3 apps)
npx cap sync android (3 apps)
```

No se desplegó, no se publicó, no se hizo commit y no se ejecutaron migraciones
contra bases reales. El build Gradle/APK queda no comprobado por falta de JDK y
Android SDK. `docker compose config` pasó; el build de imagen no pudo ejecutarse
porque Docker Desktop/daemon no estaba iniciado.
